## 1. 権限マトリクス

### △・×の注記

1. **[1] 公開／プライベートで分かれる**: 公開チャンネルは○。プライベートチャンネルは、自分がそのチャンネルのメンバーであれば○、メンバーでなければ×（spec §3-2, §3-3、`questions.md` Q-04）。作成者は自動的にメンバーになる（spec §3-2）ので、作成者の列は常に○になる。
2. **[2] 本人限定で、作成者にも特権は無い**: 自分が書いたメッセージだけが対象（spec §3-4「他の人が書いたメッセージは直せません」）。**チャンネルの作成者であっても、他人が書いたメッセージは編集・削除できない**。「チャンネルを作った人」列に△を置いているのは、作成者がそのメッセージの投稿者本人であるケースだけ○になるという意味で、作成者という立場そのものに編集・削除の特権があるわけではない。
3. **[3] 見える範囲が絞られる**: 一覧・サイドバーに出るのは、公開チャンネル全部と、自分がメンバーのプライベートチャンネルだけ。メンバーでないプライベートチャンネルは名前も含めて出ない（`questions.md` Q-04）。
4. **[4] 検索結果も見える範囲に限られる**: 検索結果に出るのは自分が見られるチャンネル（公開全部＋自分がメンバーのプライベート）のメッセージだけ（spec §3-6）。
5. **[5] メンバー管理はメンバーにも開かれていない**: プライベートチャンネルのメンバー一覧・追加・削除の画面を開けるのは作成者だけで、作成者ではない一般メンバーには×（`members.html`「この画面を開けるのは、プライベートチャンネルを作った人だけです」）。
6. **[6] ログイン済みは登録・ログイン画面に入れない**: `screens.md` 1章でSC-01・SC-02を「未ログイン専用」としたため、ログイン済みの社員は×（この設計判断についてはSC-01→SC-03の遷移根拠を参照）。

### 検索・公開APIがこの表に収まらない理由

上の権限マトリクスは「その機能を実行できるかどうか」を○/△/×で表している。検索（F-17）と公開API（F-18, F-19）は、実行できるかどうかという軸だけでは守りきれない機能で、**この表の○×が埋まっていることを「安全だ」の根拠にしてはいけない**。

- **検索（F-17）**: 検索という操作そのものは、ログインしている社員なら誰でもできる（表のとおり△だが、これは「実行できるか」の話）。安全性の要は「検索できるかどうか」ではなく「検索結果に何が出るか」で、これは○×という軸には出てこない。検索結果に出るメッセージは、検索クエリ自体が「本人が見られるチャンネル（公開全部＋自分がメンバーのプライベート）」だけに絞り込むことで守られている（`data.md` CRUD表 F-17行の channels/channel_user 列）。この絞り込みのSQL条件が1つでも漏れると、権限マトリクスの○×とは無関係に、見えてはいけないメッセージが結果に出てしまう。
- **公開API（F-18, F-19）**: エンドポイントそのものは誰でも呼べる（未ログインも社員も○）。安全性の要は「呼べるかどうか」ではなく「何を返すか」で、これも○×という軸には出てこない。プライベートチャンネルの情報は、チャンネル名を含めて一切返さない（spec §3-7の強い要求）。具体的には、チャンネル一覧は `type = 'public'` のものだけを返し、メッセージ一覧は対象チャンネルが公開かどうかをレスポンス生成の中で確認し、非公開なら存在しないIDと同じ404を返す（3章「エラーの返し方」）。ここが崩れると、○×の表がどれだけ埋まっていても実際は守られていない。

この2つの実際の防御は、権限マトリクスの表ではなく、`data.md`のCRUD表（検索）と3章の公開API設計（公開API）に書いてある。表を読むときは、この節とあわせて読む。

補足（実装時に追記、2026-08-18）: 認証3機能（F-01〜F-03）は **Laravel Fortify** で実装した。spec §3-1「ログインの仕組みそのものは、よく使われているやり方で構いません。作り方はお任せします」の範囲での実装判断で、上の表のURL・メソッド・遷移先はこの表のまま変えていない。あわせて次の2点を記録する。

- Fortify は上の表に無いルートも自動で登録する。使っている機能（`config/fortify.php` の `features`）を新規登録だけに絞ってもなお、`GET /user/confirm-password`・`POST /user/confirm-password`・`GET /user/confirmed-password-status` の3本が残る。いずれも `auth` 付きで、画面からの導線は無く、この設計では使わない
- パスワード再設定・メール確認・プロフィール編集・二要素認証にあたる Fortify の機能は `features` から外してある（`questions.md` Q-01 は回答待ちのため暫定で除外、Q-02 は「今回は要りません」で確定）

補足（実装時に追記、2026-08-18）: チャンネルの7本（F-04〜F-08）について、権限の再確認をどこで行うかを次のように決めた。URL・メソッド・遷移先は上の表のまま変えていない。

- **可視性の判定（404）と作成者の判定（403）は、どちらもコントローラの各アクションで行う。フォームリクエストの `authorize()` には置かない。** `authorize()` はコントローラ本体より先に走るため、そこに作成者チェックを書くと、自分に見えないプライベートチャンネルへの `PATCH` / `DELETE` に403が先に返り、チャンネルの存在が漏れる（`behavior.md` 3章「判定の順序」）。フォームリクエストは入力チェックだけを受け持つ
- **削除確認の入力がチャンネル名と一致しないときは、エラー文を出さずに編集画面（`GET /channels/{channel}/edit`）へ戻すだけにする。** `screens.md` 4章がこの欄について「エラー文は出さず、ボタンを押せない状態で表現する」と決めているため、サーバ側の再検証にも新しい文言を作らない（※設計判断: JSを無効にした利用者にだけ、設計書のどこにも無いエラー文が見えることになるのを避けた。削除が実行されないことは `behavior.md` 3章のとおりサーバ側で担保する）

## 3. 公開APIの設計

### GET /api/channels

- **認証**: 不要（spec §3-7）
- **入力**: なし
- **出力（200 OK）**: 公開チャンネルの配列。0件でもエラーにはせず空配列を返す

```json
[
  { "id": 1, "name": "全体連絡", "description": "全員に共有したいこと" },
  { "id": 2, "name": "開発", "description": "開発に関する相談と報告" },
  { "id": 3, "name": "雑談", "description": "なんでもどうぞ" }
]
```

※設計判断: 作成者名は含めない。spec §3-7「プライベートチャンネルの情報は、チャンネル名も含めて、いっさい含めないでください」という強い姿勢に合わせ、公開APIのレスポンスは「どんな部屋があるか」が伝わる最小限（id・名前・説明）にとどめた。

### GET /api/channels/{channel}/messages

- **認証**: 不要（spec §3-7）
- **入力**: パスパラメータ `channel`（チャンネルID）
- **出力（200 OK）**: 指定チャンネルのメッセージの配列。0件でも空配列

```json
[
  {
    "id": 101,
    "channel_id": 2,
    "body": "おはようございます。9月リリースの日程を今週中に確定させたいです。",
    "author_name": "鈴木 花子",
    "created_at": "2026-08-17T09:12:00+09:00"
  },
  {
    "id": 102,
    "channel_id": 2,
    "body": "承知しました。検索まわりの実装は木曜に終わる見込みです。",
    "author_name": "高橋 健",
    "created_at": "2026-08-17T09:20:00+09:00"
  }
]
```

削除済みのメッセージ（`deleted_at`が入っているもの）は結果に一切含めない。プレースホルダーすら出さない（`questions.md` Q-11の回答「外から見えるところに『削除されました』が並ぶ必要はない」のとおり）。

※設計判断: `author_name`（投稿者の表示名）は含める。spec §3-7の目的は「社内ポータルなど、別の仕組みからこのアプリの内容を読み取って表示したい」であり、誰が書いたか分からないメッセージの羅列では、この目的に対して実用性を欠くと判断した。チャンネル一覧（上記）には作成者名を含めていないが、目的が異なる：チャンネル一覧は「どんな部屋があるか」が伝われば足りるのに対し、メッセージ一覧は会話の中身を見せることが目的で、投稿者は表示の最低限の一部と判断した。この2つの判断は `data.md` の3章・4章（F-18/F-19のusers列）にも反映済み。

**暫定で決めた点**（`questions.md` Q-10・Q-11・Q-12 は回答待ち。回答が来たらここを直す）:

- **編集済みメッセージをどう示すか**: Q-11の該当箇所が未回答。**暫定**として、編集済みを示すフィールド（`edited`など）は持たせない。上の例のキー以外は返さない
- **スレッドの返信をこの一覧に含めるか**: Q-12が未回答。**暫定**として、返信（`parent_message_id`が入っている行）は含めず、元メッセージ（`parent_message_id`がNULLの行）だけを返す
- **全件を一度に返すか、ページングを設けるか**: Q-10が未回答。**暫定**として、ページングは設けず全件を1回で返す

3つとも実装を進めるための暫定で、`questions.md` の同じQにも「暫定」として記録してある。クライアントの回答が来たら、`questions.md` とこの節の両方を直す。

### エラーの返し方

存在しないチャンネルIDと、非公開（プライベート）チャンネルのIDは、**どちらも同じ404**を返す。

```
HTTP/1.1 404 Not Found
```
```json
{ "message": "指定されたチャンネルが見つかりません" }
```

存在有無で応答を変えると、「このIDのプライベートチャンネルは存在する」という情報自体が漏れる。`questions.md` Q-04でクライアントが求めた「メンバーでないプライベートチャンネルは、存在自体が分からない状態にしたい」という考え方を、公開APIにもそのまま適用した。

それ以外の予期しないエラー（500番台）は、この設計では個別に定義せず、Laravel標準の挙動に任せる。
