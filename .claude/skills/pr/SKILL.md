# プルリクエストを出す

イシューの受け取りは PR でやります（CLAUDE.md）。受け入れ条件を**人が1行ずつ確かめる**ための材料を本文に揃えるのが、この手順の目的です。

## 出す前に確かめる

- 作業ツリーがクリーンか（`git status --short`）。消し忘れの一時ファイルが混ざっていないか
- `./vendor/bin/sail php vendor/bin/pint` と `./vendor/bin/sail artisan test` が通るか
- 設計で決めたことが変わったなら、`docs/design/` の該当ファイルが**同じブランチに入っているか**。コードだけ直して済ませない（`docs/design/README.md`）
- ブランチが最新の `main` から分岐しているか。離れているなら先に取り込む

## 本文に載せる3つ

CLAUDE.md が決めている3つを、次の作り方で埋めます。

### 1. テストの実行結果

**そのとき回し直した出力を貼ります。**記憶から書いたり、前に見た結果を写したりしません。人はこの出力を見て「本当に通っている」と判断するので、実物でないと意味がありません。

失敗ではない警告（PHP の Deprecated など）が混ざるときは、消さずに貼ったうえで「失敗ではないこと」と「何が原因か」を1行添えます。都合の悪い行を落とすと、次に同じ出力を見た人が原因を追い直すことになります。

### 2. 受け入れ条件ごとの判定

`docs/design/acceptance.md` から、そのイシューの `AC-<単位番号>-<連番>` を1行ずつ引きます。**番号と条件文はそのまま写します。**実装に合わせて条件を書き換えたら、それは条件ではなくなります。

各行に、満たしたかどうかと、**何で確かめたか**を添えます。テストのメソッド名と、ブラウザで見た画面の両方があると、読む人が追試しやすくなります。

イシューの範囲が受け入れ条件より狭いとき（一覧の中身は次の実装単位、など）は、どこまでを今回の判定にしたのかを1行足します。

### 3. `Closes #<イシュー番号>`

本文の最後に置きます。

ここで順序がぶつかります。Claude Code の既定は「PR 本文の末尾に `🤖 Generated with Claude Code` のフッターを置く」で、CLAUDE.md は「`Closes` を最後に置く」です。**フッター → 空行 → `Closes #N`** の順にして、CLAUDE.md の決めを優先します。GitHub は位置に関係なくイシューを閉じるので、どちらでも動きますが、決めごとがある側に合わせます。

## あわせて載せるもの

**設計書の追記**があるなら、どのファイルの何章に何を足したかを並べます。「コードより先に設計書を直す」を守ったことが、読む人にはこれでしか分かりません。

**実装で判断したこと**のうち、設計書に根拠が無くて選んだもの（使ったライブラリ、既定の打ち消し方など）も短く書きます。差分だけ見ても理由が分からないところです。

## 出しかた

タイトルはイシューのタイトルを引きます。自分で言い換えません。

本文は heredoc で流し込まず、**リポジトリの外**（スクラッチパッド）にファイルとして書いてから渡します。日本語と改行が崩れず、リポジトリに置き忘れてコミットに混ざる事故も防げます。

```bash
git push -u origin <ブランチ名>
gh pr create --base main --title "<イシューのタイトル>" --body-file <スクラッチパッドのパス>
```

出したら URL を報告します。

## この部品の範囲

PR を出して URL を報告するところまでです。**マージはしません。**取り込むかどうかは人が決めます。

出したあとの下読みは `review-diff`、画面での受け入れ確認は `uat` が受け持ちます。
