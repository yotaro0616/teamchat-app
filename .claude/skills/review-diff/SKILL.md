# 差分の受け取り

対象のプルリクエストの番号が渡されたら、`gh pr diff <番号>` で差分を出します。番号が渡されていないときは、いまの作業ツリーの差分を対象にします。

## 読む順番

1. `docs/design/` にあるその機能の設計書と突き合わせる。書いていないものが増えていないか（`composer.json` に注意）
   - どれを見るかは機能で決まる。画面の項目・入力チェックとエラー文は `screens.md`、テーブルとCRUDは `data.md`、権限・ルーティング・公開APIは `permissions-api.md`、状態と例外方針は `behavior.md`、受け入れ条件は `acceptance.md`。
   - 設計書と実物が食い違っていたら、コードだけ直して済ませない。設計書を先に直す約束になっている（`docs/design/README.md`）。
2. 触っていないはずの場所を見る。消えた行から先に
   - `routes/web.php`・`routes/api.php`（公開APIは読み取りの2本だけ。書き込み系が増えていないか）
   - チャンネルの可視範囲を絞っている場所（自分がメンバーでないプライベートを一覧・サイドバー・検索から外す条件）
   - メッセージの本人確認をしている場所（`app/Http/Controllers/MessageController.php`。`behavior.md` 2章のシーケンス図の当事者）
   - チャンネル画面のビュー（削除済みメッセージのプレースホルダ表示・「編集済み」の印・返信件数）
3. 中身を読む。N+1・認可の置き場所・マスアサインメント・XSS・CSRF・入力チェック・書き方の揃い
4. このリポジトリで漏れやすいものを見る
   - 検索（F-17）と公開API（F-19）に `deleted_at IS NULL` が入っているか。入れ忘れると削除済みの本文が漏れる
   - 逆にチャンネル表示（F-06）・スレッド表示（F-16）で削除済みが消えていないか。ここは全件出す
   - 自分がメンバーでないプライベートチャンネルが、403 ではなく存在しないIDと同じ 404 になっているか
   - 公開APIのレスポンスにプライベートチャンネルの情報が混ざっていないか（チャンネル名も含めて）
   - 画面で隠しているだけになっていないか。作成者チェック・投稿者本人チェック・削除確認入力の一致は、サーバ側でも再検証する

## 報告のしかた

観点 / 判定（要確認・OK・対象外）/ ファイル名:行番号 / 気づいたこと の順で1行ずつ書きます。

判定できないときは、何が足りなくて判定できないのかを書きます。

最後に、人が自分の目で読むべき場所を3つまで挙げます。
