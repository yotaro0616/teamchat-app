# 差分の受け取り

対象のプルリクエストの番号が渡されたら、`gh pr diff <番号>` で差分を出します。番号が渡されていないときは、いまの作業ツリーの差分を対象にします。

## 読む順番

1. `docs/design/` にあるその機能の設計書と突き合わせる。書いていないものが増えていないか（`composer.json` に注意）
   - どれを見るかは機能で決まる。画面の項目・入力チェックとエラー文は `screens.md`、テーブルとCRUDは `data.md`、権限・ルーティング・公開APIは `permissions-api.md`、状態と例外方針は `behavior.md`、受け入れ条件は `acceptance.md`。
   - 設計書と実物が食い違っていたら、コードだけ直して済ませない。設計書を先に直す約束になっている（`docs/design/README.md`）。
2. 触っていないはずの場所を見る。消えた行から先に
   - `routes/web.php`・`routes/api.php`（公開APIは読み取りの2本だけ。書き込み系が増えていないか）
   - チャンネルの可視範囲を絞っている場所（自分がメンバーでないプライベートを一覧・サイドバー・検索から外す条件）
   - メッセージの本人確認をしている場所（`app/Http/Controllers/MessageController.php`。`behavior.md` 2章のシーケンス図の当事者）
   - チャンネル画面のビュー（削除済みメッセージのプレースホルダ表示・「編集済み」の印・返信件数）
3. 中身を読む。N+1・認可の置き場所・マスアサインメント・XSS・CSRF・入力チェック・書き方の揃い
4. このリポジトリで漏れやすいものを見る
   - 検索（F-17）と公開API（F-19）に `deleted_at IS NULL` が入っているか。入れ忘れると削除済みの本文が漏れる
   - 逆にチャンネル表示（F-06）・スレッド表示（F-16）で削除済みが消えていないか。ここは全件出す
   - 自分がメンバーでないプライベートチャンネルが、403 ではなく存在しないIDと同じ 404 になっているか
   - 公開APIのレスポンスにプライベートチャンネルの情報が混ざっていないか（チャンネル名も含めて）
   - 画面で隠しているだけになっていないか。作成者チェック・投稿者本人チェック・削除確認入力の一致は、サーバ側でも再検証する

## 決めごとに沿っているか

読む順番の3・4が「壊れていないか」を見るのに対して、ここは「このアプリで決めたとおりか」を見ます。外れていても直さず、**直したほうがよい場所として報告します**。設計書のどこに反しているかを必ず添えます。

**整形の揺れとテストの合否は書きません。**フックが編集のたびに回しているので、報告に混ぜると人が読む量が増えるだけです。

### 設計書と実物の、どちらが動いたか

- 実装が設計と違うとき、`docs/design/` の該当ファイルが同じ差分に入っているか。コードだけ変わっていたら報告する（`docs/design/README.md`「実装中に決めが変わったら、コードではなくここを先に直します」）
- `docs/spec.md` と `mockup/` が変更されていないか。この2つはクライアントからもらったもので、差分に出てきたらそれだけで報告に値する
- `questions.md` で「回答なし」「一部回答」のままの項目を、実装が黙って確定させていないか。暫定で進めるなら「暫定」と明記されているか。とくに検索（F-17）と公開API（F-18/F-19）

### 画面が見本のとおりか

ピクセル一致は見ません。見るのは並び・項目・言葉づかい・状態の見せ方です。

- 日時が `2026/08/17 14:32` の形で統一されているか
- エラー文が1文・句点なしか。`screens.md` 4章に文言が決まっているものは、その文言そのままか
- 画面に出すアプリ名が「チームチャットアプリ」で揃っているか
- 空・0件、押せないボタン、編集中、削除の確認が `design-guide.md` §4 の型に乗っているか。**押せないボタンを非表示にしていないか**（隠すのではなく、押せない状態で見せると決めてある）

### JavaScript が決めた範囲を超えていないか

- 使ってよいのは、文字数カウンタの追随表示と、それに連動する送信・実行系ボタンの活性/非活性だけ
- 画面遷移をJSでやっていないか。`PATCH`／`DELETE` が `@method()` のメソッド偽装で送られているか
- スレッドパネルと削除確認カードが、専用URL・同一ページ内アンカーで実現されているか

### 業務ルールがサーバ側にあるか

UIで隠す・押せなくするのは見た目の話で、判定はサーバ側にも要ります。

- 返信の1段制限（返信をさらに親にできない）がアプリ側でチェックされているか。DB制約には無い
- 作成者を自分のチャンネルのメンバーから外せない、が守られているか
- 公開範囲が編集フォームに無いだけでなく、`PATCH` が `type` を受け取っていないか
- チャンネル名の重複不可が、DBのUNIQUEとバリデーションの両方にあるか

### データの持ち方が `data.md` のとおりか

- メッセージの削除で `body` がクリアされていないか。`deleted_at` だけを更新しているか
- 「編集済み」の判定に `updated_at` を使っていないか（`edited_at` を専用に持つと決めてある）
- 返信件数のキャッシュ列を足していないか（都度 `COUNT` と決めてある）
- チャンネルの削除が物理削除で、`channel_user` と `messages` が CASCADE で落ちるか
- メッセージの並びが古い→新しいか

### 受け入れ条件と初期データ

- そのイシューの `AC-<単位番号>-<連番>` がPR本文に1行ずつ挙がっていて、判定が書かれているか
- `acceptance.md` の受け入れ条件が、実装に合わせて書き換えられていないか。条件を実装に寄せたら、それは条件ではなくなる
- 受け入れ条件やテスト観点に対して、テストが無い箇所がどこか（合否ではなく、**手が付いていない観点**を挙げる）
- シーダーが spec §5-4 のとおりか。アカウント3件のメールとパスワード、チャンネル4件、返信が付いたメッセージ2件以上（うち1件は返信3件以上）、編集済み1件以上、削除済み1件以上、プライベートにも数件

## 報告のしかた

観点 / 判定（要確認・OK・対象外）/ ファイル名:行番号 / 気づいたこと の順で1行ずつ書きます。

判定できないときは、何が足りなくて判定できないのかを書きます。

最後に、人が自分の目で読むべき場所を3つまで挙げます。

## この部品の範囲

コードは直しません。読んで報告するところまでです。
