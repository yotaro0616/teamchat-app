# イシューに着手する

`$ARGUMENTS` は、着手したいイシューの番号です（`#4` のような形）。

計画を出して承認をもらうところまでが範囲です。手を動かし始めるのは、そのあとです。

## モードの切り替え

計画は Plan モードで出します。承認の関門がそのまま使えるので、自前で「これでいいですか」と聞く必要がありません。

順番に気をつけます。**手順1のブランチ作成は編集にあたるので、Plan モードに入る前に済ませます。**入ってからでは `git switch` も `git branch -d` も実行できません。

1. 通常モードのまま、手順1（ブランチ）を終える
2. `EnterPlanMode` を呼ぶ。呼ぶと承認を求めるプロンプトが出るので、そこで人が入る
3. 手順2〜6（調査・質問・計画）は Plan モードの中でやる。ここは読むだけなので通ります
4. 計画を書き終えたら `ExitPlanMode` で承認をもらう

すでに Plan モードで呼ばれたときは、`EnterPlanMode` を呼び直しません。ブランチは切れないので、そのことを伝えて計画の先頭に「承認後にブランチを切る」と入れておきます。

## 手順

### 1. ブランチを用意する

`main` に切り替えて `origin` から pull し、そこからブランチを切ります。`main` に直接コミットしません（CLAUDE.md「イシュー1件につきブランチ1本」）。

名前は既存に合わせて `feat/<短い英語>`。切る前に `git branch -vv` を見て、`main` と同じコミットのまま残っているブランチがあれば、消してよいかを聞きます。黙って消しません。

### 2. イシューを読む

`gh issue view <番号>`。本文の**「変えないもの」と「このイシューで作らないもの」**の節を落とさずに読みます。ここに書いてあることは、もう決まっていることです。あとで「決めが要る」として聞き返すと、答えたことをもう一度聞かれる形になります。

### 3. 設計書とモックアップを、原文のまま調べる

Explore サブエージェントに投げると速く、2本に分けて並行で走らせるのが具合よく収まります。

- **設計書側** — `docs/spec.md` の該当節と、`docs/design/` の該当章（画面と文言は `screens.md`、テーブルは `data.md`、URLと権限は `permissions-api.md`、例外方針は `behavior.md`、受け入れ条件とテスト観点は `acceptance.md`、未確定は `questions.md`）
- **見た目と現状側** — `mockup/` の該当HTML、`mockup/design-guide.md`、`mockup/styles.css`、そしていまのコードがどこまで出来ているか（`composer.json`・`routes/`・`app/`・`database/migrations/`）

投げるときは**「要約せず原文をそのまま引いてほしい」と明記します**。画面の文言・エラー文・上限値は一字一句が正本で、要約されると使えません。言い換えられたものを信じて実装すると、`screens.md` 4章と違う文言が画面に出ます。

### 4. 環境を確かめる

- `.claude/settings.json` — 書き込み禁止の場所（`docs/spec.md` と `mockup/`）と、編集のたびに何が走るか
- Sail が上がっているか（`docker compose ps` の mysql が `Up (healthy)`）
- `vendor/` と `node_modules/` があるか

ここを先に見ておくと、計画の中で「npm が要るのか要らないのか」「テストが実DBに繋がるか」を決められます。あとから気づくと計画を書き直すことになります。

### 5. 決めが要るところだけ聞く

**聞かないこと**（設計書で決まっているので、読めば分かる）

- URL・HTTPメソッド・遷移先（`permissions-api.md` 2章）
- 画面の項目・文言・エラー文（`screens.md` 3章・4章、`design-guide.md` §4）
- 入力の上限値（`docs/spec.md` §5-1）
- テーブルの列（`data.md` 2章）
- `questions.md` で回答済みの項目

**聞くこと**

- 設計書のどこにも根拠が無くて、どちらを選ぶかで作業の中身が変わるもの（使うライブラリ、CSSやJSの置き場所、共通レイアウトをどこまで先に作るか）
- 設計書どうしが食い違っていて、片方に寄せないと進めないところ

`questions.md` が「回答なし」「一部回答」の項目は、勝手に確定させません。暫定で進めるなら、**`questions.md` と該当の設計書の両方**に「暫定」と書き残すところまでを計画に入れます。片方だけだと決まりを外します（CLAUDE.md）。

### 6. 計画を出す

節はこの8つ。

1. **Context** — なぜこれをやるのか。いま何ができないのか
2. **このターンで決めたこと** — 5で聞いて決まったことを表で
3. **作業手順** — 触るファイルと、そこで何をするか
4. **変更するファイル** — 新規・変更・削除
5. **進めかたの注意** — 途中でテストが赤くなる区間など、先に言っておくこと
6. **検証** — 動かすコマンドと、ブラウザで確かめる手順
7. **PR** — 本文に載せるもの
8. **調べて分かったこと** — 3で読んだ原文のうち、実装に要るものの引き写し

8つめは、実装を `implement` エージェントに渡すために要ります。あのエージェントは**この会話を引き継ぎません**。3で調べて分かったこと（モックアップにその見本が無い、CSSに切り替えの規則が無い、といった「読んで初めて分かること」）は、計画に書いていなければ伝わりません。

書くのは次の3種類だけです。設計書を読み直せば済むことまで写すと、計画が設計書の写しになってしまいます。

- **一字一句が要るもの** — 画面に出す文言・エラー文・placeholder・上限値。言い換えると `screens.md` 4章と違うものが画面に出ます
- **在りかの対応表** — 「この画面のこの項目は `screens.md` 3-5」「このURLは `permissions-api.md` 2章」。実装が開くべき場所を指しておきます
- **読んで初めて分かったこと** — モックアップに見本が無い状態、CSSに規則が無いクラス、既存コードの手がかり（似た画面のBladeやテストの型）。ここが抜けると、渡した先で同じ調査をやり直すことになります

## 計画に必ず入れるもの

3つ。抜けると、あとで受け取りのところで止まります。

- **設計書の追記** — 実装で決めたことが設計書に無いなら、コードより先に `docs/design/` を直します（`docs/design/README.md`）。どのファイルの何章に何を足すかまで書きます
- **受け入れ条件の確かめ方** — そのイシューの `AC-<単位番号>-<連番>` を1行ずつ挙げ、どのテストとどのブラウザ操作で確かめるかを書きます。条件そのものは書き換えません
- **PR に載せる3点** — テストの実行結果／受け入れ条件ごとの判定／最後に `Closes #<番号>`（CLAUDE.md）

## この部品の範囲

計画を出すところまでです。承認より前に、アプリのコードは書きません。設計書も直しません（計画の中で「こう直す」と書くだけです）。ブランチだけは例外で、`ExitPlanMode` の承認を待たずに先に切ります。

## 承認をもらったら

実装は `implement` エージェント（`.claude/agents/implement.md`）に渡します。渡すのは次の3つです。

- 計画ファイルのパス（`~/.claude/plans/*.md`）
- イシュー番号
- ブランチ名

あちらは設計書を先に直してからコードとテストを書き、テストを緑にしてコミットまでして、変更点と判断だけを返します。読み込んだ設計書やテストの出力はあちらのコンテキストに置いたままになるので、こちらは計画と報告だけを持っていられます。

1〜2ファイルで終わる小さな直しは、渡さずにそのまま実装しても構いません。渡す手間のほうが大きくなります。
